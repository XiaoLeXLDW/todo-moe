## 目标与范围

交付一个能证明“从指定源码可重建、以独立身份安装、连续覆盖升级后测试数据仍正确”的 Android 开发版。先建立可验证基线，再做 UI 改造。

| 纳入范围 | 本版不做 |
|---|---|
| 核对并锁定 Mindwtr 上游 tag、SHA、依赖、构建和检查命令 | 不把历史聊天中的版本、路径或命令当作已核对事实 |
| 保留上游 Git 历史、许可和已有说明；规划 origin/upstream 关系 | 本次整理不创建远程 Fork；实际开发也不覆盖已有仓库内容 |
| 集中品牌配置、开发版身份、版本与上游追溯信息 | 不全仓库替换 Mindwtr，不改协议字段、内部包名或作者声明 |
| 原版与改品牌版构建、安装、两次连续覆盖升级、数据隔离演练 | 不重构导航，不加玻璃，不改任务完成、重复任务或同步算法 |
| 本地测试数据与独立云端测试目录、备份/恢复基线 | 不把开发包直接连接真实日用同步目录，不迁移真实待办 |

用户明确要沿用家族品牌；`Todo Moe`、`Todo Moe Dev`、`io.github.xiaolexldw.todomoe` 及仓库名均是历史建议或示例，未定稿。可以先用可辨识的临时开发身份，但正式身份必须在首个日用发行前定下。

## 本版具体功能

开发版可从桌面图标与“关于”页明确识别，避免误用日用包。Debug 构建并不自动使用独立 Dev 包名，最终需检查 APK manifest 和实际安装包信息。启动画面、应用名、图标、包名、URI scheme、更新来源、第三方服务回调逐项核对；更改 package ID 后，任何依赖服务身份的行为都重新验证。

版本信息能追溯到源码；一次构建的 APK 和记录中版本一致。Dev 使用独立测试任务及独立远端同步位置；仅改包名不能作为云端数据隔离证据。原版支持的任务创建、编辑、完成、重启保存、导入导出和拟用同步路径，应保留功能基线。“Mindwtr Cloud”是自托管服务，不预设官方已有托管账号；选定构建类型实际支持哪些同步后端须列表核对。

正式签名身份本版形成方案。若正式候选包尚未产生，只能宣称“Dev 覆盖升级通过”；不能替代正式签名发行渠道的验收。

以下 `V01-*` 是 [统一 QA 矩阵](../05-测试与发布维护.md#2-测试矩阵) 的本版细项：V01-01→QA-01；V01-02/04/07→QA-02；V01-03→QA-03；V01-05/06→QA-10；V01-08→QA-13 的秘密保护检查；V01-09→QA-11。

| 用例 | 操作与观察 | 通过条件 |
|---|---|---|
| V01-01 可重建 | 使用记录中的干净检出与锁定依赖执行真实检查、构建命令 | 成功生成 APK；源码 SHA、环境和所有命令可追溯。尚未证明字节级可重复时，不声称二进制哈希必然相同 |
| V01-02 并存身份 | 先确认既有日用包，再安装 Dev；读取实际包信息并分别启动 | 两者包名不同、签名记录正确、图标/标题可区分，既有包数据未变 |
| V01-03 核心基线 | 在 Dev 创建文件夹对应实体、清单、任务；编辑、完成、撤销、重启 | 操作结果与选定上游一致，重启数据保留；不存在 UI 改名导致的数据变形 |
| V01-04 连续升级 | A 中准备含未完成、已完成、重复任务的样本；A→B→C 同身份正常覆盖升级 | 两次均成功安装，`versionCode` 单调增加，签名兼容，记录逐项一致，无需卸载清数据 |
| V01-05 云端隔离 | 用两个隔离测试客户端与不同测试目录模拟 Stable/Dev，各放入可辨识样本并同步；真实日用端只读核对配置 | 两组样本各自在指定测试空间变化、互不读写；真实日用数据未被写入或拿来演练 |
| V01-06 备份与恢复 | 导出测试数据，另建隔离测试环境导入，离线编辑后恢复连接同步 | 数据数量、关键字段和状态一致；冲突/重复/错误能被定位，失败不覆盖唯一备份 |
| V01-07 身份配置 | 实测需用的深链/回调及关于页；查看第三方归属与许可 | 所有已启用入口匹配自有身份；不可用入口明确关闭或列阻塞，作者与许可保留 |
| V01-08 秘密检查 | 检查版本记录、Git 变更、构建日志和产物列表 | 无签名私钥、口令、同步凭据或真实待办泄漏；仅保留指纹和脱敏路径 |
| V01-09 原有系统能力 | 在隔离环境检查选定基线已有的提醒、Widget、通知、权限和后台行为 | 品牌/包身份变更未使实际启用能力失效；系统限制与未支持功能单独记录 |

本版通过要求 V01-01～09 按实际纳入范围完成；尚无设备或测试同步端时保留“未验证”，不能以编译成功放行数据与升级结论。

## 失败分支与回退

| 失败位置 | 处理方式 | 恢复条件 |
|---|---|---|
| 未修改上游也构建失败 | 先确认依赖、平台和实际命令，固定最小失败日志；暂停品牌接入 | 原版基线构建先通过 |
| 改品牌后失败 | 回退本版品牌接入提交，逐项恢复配置；不全局改名重试 | 原基线可运行，问题定位到具体身份或资源配置 |
| 覆盖升级拒绝 | 比对包名、签名证书、`versionCode` 和安装错误；不以卸载绕过验收 | 同身份升级成功，失败原因有记录 |
| 同步跨入日用目录 | 停止 Dev 同步操作，保存脱敏现场与原备份，先评估影响 | 独立端点/目录确认且污染处理方案经核对；不盲目覆盖云端 |
| 数据恢复不一致 | 保留样本与导出，定位上游原行为或本版引入差异 | 可重复恢复并比对通过；旧 APK 不视为数据库回滚方案 |
