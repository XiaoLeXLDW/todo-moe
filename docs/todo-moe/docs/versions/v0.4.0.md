## 目标与范围

让常规的上游版本发现、同步 PR、检查和测试 APK 构建可以重复执行，让正式发行能从批准的确定提交追溯到签名 APK 与手机更新结果。异常必须停在可诊断位置。

| 纳入范围 | 本版不做 |
|---|---|
| 上游稳定版本检查、单个待处理同步 PR、冲突报告 | 不跟随每个 main 提交自动发日用版，不强推覆盖自有改动 |
| 类型检查、相关测试、Android 测试构建与结果汇总 | 不把“PR 创建成功”当 CI 已跑，不把 APK 附件当正式 Release |
| 基于明确提交的受控正式签名、校验、Release 草稿/发布流程 | 不在不可信 PR/自动修复任务中暴露正式签名密钥 |
| GitHub Releases + Obtainium 候选更新渠道 | 不自写更新器，不默认静默安装或设备已装 Obtainium |
| 成功、冲突、测试失败、重试、触发失效及回退演练 | 不启用全部上游商店/桌面/iOS 发布流程，不用 AI 处理例行确定性操作 |

“每天检查稳定 Release”“集中一个同步 PR”“GitHub Releases + Obtainium”“发布前由用户验收”均是历史建议，本版采用为待落地默认方案；真正的频率、远程仓库和发行范围需在启用前记录。用户现在授权的是整理文档，并非已经授权公开仓库、上传包或设置长期运行任务。

## 开发任务与候选代码位置

| 步骤 | 动作 | 候选位置（未克隆待确认） | 结果 |
|---|---|---|---|
| 1 | 审计上游 Android 构建及仓库权限，提炼自有流程，关闭不负责的发行入口 | `.github/workflows`、现有 scripts、Android 构建配置 | 工作流列表、权限与触发关系图 |
| 2 | 编写确定性上游发现与合并脚本：建立同步分支后尝试 merge，成功才创建/更新 PR；按 tag/SHA 去重并保留 upstream 合并历史 | 候选 `moe-sync-upstream.yml` 和 `scripts/moe` | 新版本/无更新/已处理/冲突的明确结果；成功时一个待处理 PR，冲突时问题报告/Issue |
| 3 | 建检查与 Dev 构建流程，用显式调用链或经验证的触发方式保证 CI 真正执行 | 候选 `moe-check.yml`、可复用工作流或合适的显式触发 | 每个 PR 的工作流运行 ID、检查结果及 APK 哈希 |
| 4 | 建受控发行流程：批准确定 SHA→重验→签名/验证→发布对应产物和源码说明 | 候选 `moe-release-android.yml`、版本/签名/Release 脚本 | Stable 版本记录、证书指纹、签名日志、Release 与 APK |

三个 `moe-*` 名称是建议名称，最终工作流按实际仓库组织。Codex 自动修复 PR 是后续可选扩展，不作为本版必需依赖；不能假定 Codex 桌面订阅或登录态自动供 CI 使用。

## 具体流程与失败行为

| 阶段 | 成功行为 | 异常行为 |
|---|---|---|
| 检查上游 | 识别未处理稳定版本并固定 tag 与完整 SHA | 网络/API 失败可重试并报错；无新版本安静结束；无稳定版标记时按预设规则处理，不猜测 main 即稳定 |
| 同步分支/PR | 先建立同步分支并尝试 merge；合并成功才创建/更新 PR，保留自有代码与上游祖先关系 | 冲突停止，产出含文件与双方 SHA 的报告/Issue；不在首次无差异时先创建 PR，不强推主分支或丢弃自有修改 |
| 检查与测试 APK | 对待合入确定 SHA 跑检查并产出隔离 Dev 包 | 任一必要检查失败阻止后续发行；PR 已有但工作流没运行仍视为失败/待处理 |
| 验收与批准 | 用户看到具体 commit、APK 哈希、变更摘要、测试与未验事项 | commit 改变则原批准失效；数据库/同步/任务逻辑/权限/签名/工作流变化单列评审 |
| 正式签名/Release | 构建经过同等检查的正式候选，核对包名/versionCode/证书，发布对应 APK 和源码记录 | 签名、证书、版本或文件校验失败不发布；先签名后再写 Release 状态，不留下假成功 |
| 手机更新 | 稳定渠道只发现 Stable，新包覆盖旧包后数据正确 | Dev 不被识别成稳定更新；不兼容包给出明确错误，不通过卸载日用包强行完成 |

若批准的是 Dev APK，正式包因身份/配置不同，不能声称二者是同一个二进制。应记录批准的源码 SHA、正式构建差异与正式候选的必要补验；用于日用发行的 APK 哈希必须最终固定，并与下载结果核对。

自动化报告应记录上游版本/SHA、自有合并前后 SHA、涉及模块、是否有数据迁移/同步/权限/完成逻辑/签名/工作流变化、检查运行 ID、失败日志、APK 版本及哈希。不能只写“自动同步成功”。

## 签名、版本、渠道和触发约束

| 项目 | 本版要求 |
|---|---|
| 正式签名 | 从 v0.1.0 的固定身份延续；秘密仅在受控签名环节可用；PR、不可信构建和自动修复任务不可读取；日志只留指纹 |
| `versionCode` | 对正式身份统一递增并处理并发、重跑与已发布版本；拒绝重复使用旧值发布不同 APK |
| Stable / Dev | 包名、签名、Release/预发布筛选与独立同步位置逐项验证；同一个仓库并不自动保证渠道分离 |
| Git 追溯 | 上游同步保留可识别合并历史，记录上游 tag/SHA；发布 tag 指向批准 commit，APK 的关于页匹配 |
| 触发链 | 核对当前平台对机器人 token、PR 事件、工作流审批的行为，实际演练；不能假设机器人开 PR 后所有 CI 自动运行 |
| 定时可用性 | 有手动触发和最后成功检查时间；平台可能禁用闲置定时任务，具体规则以当前核对为准 |
| 许可与源码 | 发布前保留上游与第三方声明、来源清单、对应修改源码及构建说明；按实际引入代码核对，不能仅换名就改为 MIT |

分发或公开仓库属于后续执行动作。本版计划中的受控发布是把内容做成可审阅的具体产物再执行发行，不能把本次文档整理写成已有发布授权或发布成功记录。

## 验收用例与通过条件

以下 `V04-*` 是 [统一 QA 矩阵](../05-测试与发布维护.md#2-测试矩阵) 的本版细项：V04-01→QA-12/13；V04-02/03/04/05/08→QA-12；V04-06/07/09→QA-13。记录模板见 [上游同步记录](../templates/上游同步记录模板.md) 与 [版本记录](../templates/版本记录模板.md)。

| 用例 | 演练 | 通过条件 |
|---|---|---|
| V04-01 正常闭环 | 以测试仓库/隔离分支模拟新稳定上游，从发现到 PR、CI、Dev APK、批准、正式候选和更新 | 每环节有 SHA/运行 ID/哈希；下载包一致；实机覆盖升级并保留测试数据 |
| V04-02 幂等与无更新 | 同一上游版本连续触发，重复运行失败步骤，再执行无新版本检查 | 不创建重复 PR/Release，不混淆旧产物，不复用冲突 versionCode，结果能追溯 |
| V04-03 合并冲突 | 人为构造同一文件冲突 | 工作流停止，主分支和日用发行不变；报告冲突文件、两端 SHA 和恢复入口 |
| V04-04 测试失败 | 在测试分支注入可控检查失败 | 不发布；报告实际失败日志；修复后重新对新 SHA 检查并申请对应验收 |
| V04-05 触发与权限 | 验证机器人 PR 后 CI 实际启动；从不可信 PR 尝试走发行入口 | 正常链路有真实运行记录；不可信任务无法获取正式秘密或自行批准发行 |
| V04-06 签名与版本 | 正常同证书升级；构造错误证书、旧 versionCode 与包名错配的测试输入 | 校验在发布前拒绝错误产物；不把安装失败解释成可卸载解决 |
| V04-07 渠道筛选 | 为 Stable 与 Dev 产生可区分测试 Release/附件，检查 Obtainium 识别结果 | 各自只选目标包/渠道；稳定用户不会接收 Dev；安装仍由既定方式确认 |
| V04-08 定时失效与手动恢复 | 暂停测试定时入口并执行手动检查，查看最后成功时间和异常报告 | 能恢复检查，状态明确，不依赖定时永久运行 |
| V04-09 部分发布与回退 | 模拟上传中断、重复调用、坏版本候选撤回以及向前修复 | 不出现“Release 成功但 APK 缺失/哈希错误”；修复保持版本递增，数据兼容另验 |

真实 GitHub 与手机链路未演练时，仅可标注脚本/静态验证通过。不得写“自动更新已打通”。

## 回退与恢复

上游同步失败时保留失败分支与日志，已发布版本继续使用。修复应形成新提交并重新检查。对坏候选停止发行；已分发的问题包应优先构建版本号更高的修复版，并说明影响与数据恢复条件。

回退源代码不等于回退本地数据库或云端数据。涉及迁移时先验证备份与恢复、跨版本读写边界；不尝试用旧 APK 覆盖新数据来“证明回滚”。签名秘密泄漏、丢失或证书不一致应停止该身份发行，记录恢复/迁移方案，不能重新生成密钥后假定已有用户可正常升级。
