# 架构与工程方案

**以 Mindwtr 的既有业务与数据能力为基础，把品牌、主题、动画与玻璃集中成移动端定制层。** 下列架构约束与候选方案形成于开发前；当前已有源码、Dev构建和原版对照。实际路径、提交及命令见 [执行台账](../IMPLEMENTATION.md) 和 [Windows构建说明](../WINDOWS-BUILD.md)。

## 1. 建立可追溯的上游关系

建议在用户自己的 GitHub 账号下建立 Fork，保留上游历史，origin 指向个人仓库、upstream 指向官方 Mindwtr。源码接入时已将Git仓库置于工作区的todo-moe子目录，保留原文档，并将文档复制入仓库管理。

建议一个长期主分支 main，功能使用 feat/…，上游接入使用 sync/mindwtr-…。实际origin为XiaoLeXLDW/todo-moe，开发分支为feat/todo-moe。默认采用 merge + PR 接入上游，保留合并历史，不用强制覆盖丢弃定制。

获取源码后先读取并保留上游现有 AGENTS.md 及相关工程指导，再按本项目已确定的范围追加维护约束，记录新增内容的来源；不覆盖原有指导。上游CONTEXT.md已保留，新增AGENTS.md只记录本fork的维护边界和证据入口。该工作属于v0.1.0工程基线。

| 基线字段 | 应记录内容 | 方案阶段记录（实际结果见执行台账） |
|---|---|---|
| 上游仓库 | 官方 URL、默认分支 | 当前资料见 [来源核对](04-技术来源与待验证事项.md) |
| 上游版本与提交 | 选定的稳定 Release/tag 与完整 commit SHA | 未选择；文档核对的最新源码不是构建基线 |
| 本项目身份 | origin URL、分支、完整 commit、工作区是否干净 | 未建立 |
| 构建环境 | OS、Bun/Node/JDK/Android SDK/Gradle、锁文件与架构 | 未配置/未验证 |
| 原版对照 | 未改表现层的构建、签名/包信息、基础行为结果 | 未构建 |

为观察变化获取的“最新 main”与用于可复现发行的“固定稳定 tag”应分别记录。版本名相似不表示两个仓库中的源码相同。

## 2. 模块边界

```text
用户操作
   ↓
移动端定制层：品牌 / 主题 / 动画 / 玻璃 / 简化页面
   ↓
薄适配层：调用上游任务接口，映射可见词汇，处理 UI 生命周期
   ↓
上游业务、移动端存储适配、共享 core、同步与平台能力
```

| 层 | 候选放置位置 | 职责与约束 |
|---|---|---|
| 品牌 | apps/mobile 的独立 brand 配置与资源目录 | 显示名、图标、颜色、关于信息；不全局替换 Mindwtr |
| 主题/动效 | 独立 theme 与 motion/haptics 配置 | 统一数值与开关，组件不各自发明参数 |
| RN 组件 | 独立的定制组件目录 | AnimatedCheckbox、CompletionAnimation、Celebration、快速添加等 |
| 玻璃原生模块 | apps/mobile/modules/… 或上游支持的本地 Expo 模块位置 | 包含原生 View、配置/事件接口、能力检测与回退；路径未创建 |
| 业务连接 | 定制适配 hooks/service | 复用原有完成、撤销、重复任务、持久化和同步接口 |

可采用一个集中入口目录组织上述模块，也可遵循实际仓库既有结构；先审计后决定，不为目录命名本身做重构。上游页面只加入必要的导入、主题或组件接入点。

“尽量不改 packages/core”是一项降低合并成本的策略，不是数据安全证明。移动端数据库驱动、存储适配、备份和同步调用也可能位于 apps/mobile，必须一起回归。当前 SQLite 分层与驱动详情见 [技术核对](04-技术来源与待验证事项.md)。

## 3. 数据与同步约束

| 场景 | 工程规则 | 验证要求 |
|---|---|---|
| 完成/撤销/重复 | 业务调用即刻发起，动画只负责显示 | 快速连点、撤销、失败恢复、重复下一项和重启一致 |
| 组织层次 | Area/Project/Section 映射界面词汇 | 移动任务、筛选、归档后仍使用原字段与序列化 |
| Dev 与日用并存 | 各自包身份、本地空间、测试账号/同步目录 | 不同包名仍可能写同一云目录，必须检查实际目标 |
| 云同步 | 沿用上游支持且实际可用的后端 | WebDAV 兼容性、离线并发、冲突、删除与恢复均需证据 |
| 与官方桌面互通 | 作为可验证目标 | 数据格式未改仍需互通测试；不得直接宣称兼容 |

Mindwtr Cloud 的本次资料核对指向自托管服务，不能当作已经存在的官方托管账号系统。上游 WebDAV 的一致性约束与可用后端以来源资料及实际兼容测试为准。

新增 schema 或同步格式变化不在首轮计划中。若后续必要，单独版本、迁移说明、升级/恢复演练和审核同时完成，不能藏在动画改动里。

## 4. 品牌身份与构建变体

| 类别 | 要核对的项目 | 预期 |
|---|---|---|
| 用户可见 | 应用名称、图标、启动画面、通知、Widget、关于页 | 品牌一致，Dev 可辨识 |
| Android 安装身份 | applicationId、versionName、versionCode、签名证书指纹 | 正式与 Dev 分开；同渠道覆盖升级身份稳定 |
| 外部连接 | URI scheme、深链、文件 provider authority、Expo owner/projectId、Dropbox app key、分析端点与第三方回调 | 逐项确认本项目是否使用及归属，不盲用上游服务身份，避免与官方版冲突 |
| 更新来源 | Release URL、渠道、稳定/测试筛选规则 | 更新到正确包，不串 Dev 与稳定版 |
| 来源声明 | 作者、许可、第三方 NOTICE、上游与本应用提交 | 保留必要来源信息，不能全库改名消除历史 |

关于页候选显示：Todo Moe 的发行版本、构建渠道、versionCode、所基于的 Mindwtr 版本/提交和本应用提交。真实构建时生成，不能用界面硬编码冒充追溯信息。

固定发行密钥、Dev 独立密钥，记录证书 SHA-256 指纹即可。私钥、口令、同步凭据不进源码、文档或日志；具体保管位置和受控备份方式建立工程时确定。

Debug 构建类型与独立 Dev 安装身份分别检查。上游某个 debug.apk 并不自动带 .dev 包名；最终 manifest、签名和设备安装信息是判定依据，不能只看文件名。

## 5. Android 玻璃桥接

| 接口方向 | 最小内容 | 需要防止的问题 |
|---|---|---|
| RN → 原生 View | 导航项、选中项、主题、玻璃模式、底部 inset、减少动画状态 | 双端各维护一份互相冲突的导航状态 |
| 原生 View → RN | 用户选中事件、必要的能力/错误状态 | 拖动与点击重复回调；已切页后旧回调再次导航 |
| 背景来源 | RN 列表实际绘制内容到效果层的可行采样路线 | 只有静态背景或 Compose 内部内容生效 |
| 生命周期 | 挂载/卸载、页面切换、旋转、前后台 | 资源不释放、残留层、错位或恢复后不刷新 |
| 回退 | 无玻璃完整导航，柔和模式与液态模式分级 | 视觉失败导致导航消失或按钮不可点 |

优先从用户已成功使用的参考工程提取精确版本；该输入尚缺。没有输入时可核对官方来源链，但要记录替代来源，不能称为已复用用户原版本。v0.2.0 的成功标准包含动态背景、手势与性能；失败时允许选择适合 RN 的实现，只保留经过验证的路线。

不把 expo-glass-effect 的库名等同于 Android 能力；不因原生 View 能显示就认定背景采样完成；不把全部页面重写成 Compose 作为底栏验证的前置。

## 6. 构建入口与工作区安排

原聊天第二轮建议过 bun mobile:android:dev，第三轮又撤回。本次来源核对在当前上游 main 找到此脚本；见 [技术来源](04-技术来源与待验证事项.md)。这只能证明该提交定义了命令，不能证明选定稳定版本具有相同入口，更不能证明本机已构建成功。

该 Dev 路径涉及 expo prebuild --clean。引入原生模块或人工原生改动后，必须先核对生成边界、配置插件与 Git 差异，不能直接用 clean 清掉未保存的原生工程修改。

建立基线时执行下列工作并记录实际命令：

1. 核对选定提交的 package.json、锁文件、Android 工作流与构建脚本，记录版本和构建条件。
2. 先生成原版可复现对照，再增加本项目品牌与 Dev 变体，保持可解释的差异。
3. 确定原生生成/自定义方式，使干净重建后玻璃模块和配置仍存在。
4. 将构建日志、测试截图/录屏、APK 和校验文件存入可追溯的项目目录；具体工具缓存位置实施时确定。
5. 用同渠道前后两个递增 versionCode 的包验证覆盖升级与数据保留，再进入玻璃开发。

项目内建议后续采用 artifacts/<version>/、evidence/<version>/、docs/versions/ 的对应关系；这些只是目录约定，本次没有创建空 APK 或虚构证据。

## 7. 来源和许可登记

参考项目至少包括 Mindwtr、SukiSU-Ultra、compose-miuix-ui 以及实际提取到的辅助库。每项记录完整来源 commit、原始路径、本地路径、许可证文件、文件头、修改说明和发布时随附材料。

SukiSU 底栏文件的来源注释不能代表其所有辅助文件采用同一许可证。来源资料已发现多条许可链，详细见 [技术核对](04-技术来源与待验证事项.md)。在复制前逐文件核对，在发行前根据实际采用文件整理声明与对应源码；本计划不提供未经核实的“全部 Apache”结论。
