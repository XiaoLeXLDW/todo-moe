### 我最建议你先装：**Mindwtr**

这个是我这次搜下来最大的惊喜。

它是 **完全开源、免费、Local-first** 的，而且不是那种典型 FOSS “功能很好但 UI 像十年前”的应用。Android、iOS、Windows、macOS、Linux、Web 都有。citeturn774501search1turn186945search0

它的组织结构尤其符合你说的“文件夹似的多个待办”：

**Area**
→ **Project**
→ **Section**
→ Task / Checklist

比如你完全可以弄成：

> 工作  
> ├ OpenClaw  
> │　├ 本周  
> │　├ Bug  
> │　└ 后续功能  
>   
> 生活  
> ├ 买东西  
> ├ 房间  
> └ 杂事

它正式支持 **Projects + Sections + Areas**，还能手动排序；Android 端也有项目、看板、日历、Inbox 和 Focus。citeturn186945search3turn186945search4

而且同步对你应该特别合适：

**WebDAV / Dropbox / 自己服务器 / 共享目录 / 自托管 Sync Server**

它没有强制账号，默认数据就在本机。citeturn774501search15turn186945search1

甚至有 Docker、自托管 Web、REST API、CLI、**MCP Server**。这部分你以后真想折腾，还可以直接让 Agent 管你的待办。citeturn186945search8

[Mindwtr 官网](https://mindwtr.app/?utm_source=chatgpt.com)

唯一需要提醒你的：**它的完成反馈比较克制**。我没有查到它目前有那种 Todo App 很明显的 confetti / 烟花式完成动画，所以如果你要的是“啪一下勾掉，动画非常爽”，它不是最强的。

### 如果你特别看重“好看 + 完成一个任务很爽”：**Memorigi**

**Groups → Lists → Headings → Tasks → Subtasks**

## 我建议你这样二开

最重要的一条：

> **只魔改 `apps/mobile` 的表现层，尽量不要碰 `packages/core`。**

架构保持成：

```text
Mindwtr upstream
│
├─ packages/core        ← 尽量原封不动
│   ├─ 数据模型
│   ├─ SQLite
│   ├─ sync
│   └─ Zustand
│
└─ apps/mobile          ← 主要改这里
    ├─ components
    ├─ app
    ├─ hooks
    ├─ constants
    └─ animations       ← 我建议自己新增
```

这样有个巨大的好处：

**以后官方 Mindwtr 更新同步、Bug 修复、新功能，你还能继续 merge upstream。**

而不是 fork 三个月以后完全变成两个项目。

当前官方自己也是 monorepo，移动端和共享 core 已经明确分开了。citeturn705122view0turn322609view0

# 第一版我就改这 6 个地方

别一上来重画整个 App。先把**每天接触几十次的交互**做爽。

### ① 勾选任务动画

这个我觉得最重要。

现在：

```text
○ 买鸡蛋
```

点击以后不要瞬间：

```text
✓ 买鸡蛋
```

而是：

```text
点击
 ↓
圆圈缩小 0.92x
 ↓
弹到 1.15x
 ↓
✓ 画出来
 ↓
文字划线
 ↓
轻震一下
 ↓
任务轻微向右 + fade
 ↓
350ms 后从未完成列表移除
```

我会建议：

```text
checkbox
scale:
1 → 0.88 → 1.16 → 1

duration:
约 250 ms

text:
strikethrough + opacity 1 → 0.48

row:
translateX 0 → 12
opacity 1 → 0
```

最后：

```ts
Haptics.impactAsync(
  Haptics.ImpactFeedbackStyle.Light
)
```

Mindwtr **已经依赖 expo-haptics**，所以这个连包都不用加。citeturn767122view0

# 同步也不用重写

这一点才是二开最大的意义。

如果你只是：

```text
✅ 改 UI
✅ 改动画
✅ 改主题
✅ 改布局
✅ 加震动
✅ 加 confetti
```

而不去动：

```text
❌ Task schema
❌ SQLite schema
❌ Sync serialization
❌ @mindwtr/core
```

那么原则上：

```text
你的 Mindwtr Android
        ↕
WebDAV / Mindwtr Cloud
        ↕
官方 Mindwtr Desktop
```

依旧可以共用同步协议。

也就是说，你甚至可以：

> **电脑继续用官方版，手机用自己的魔改版。**

这是我最推荐的玩法。


Expo 官方有把原生 View 暴露给 React Native 的模块开发机制，可以作为桥接基础；但背景采样与具体 Compose 组件的兼容性仍需自行实现和验证。citeturn818484view4

| 验证项 | 要看到的结果 |
|---|---|
| 动态背景 | 列表滚动时，底栏后方的模糊和颜色实时变化 |
| 交互 | 点击、拖动切换、返回操作正常，不吞页面手势 |
| 布局 | 键盘弹起、底部手势区、横竖屏不遮挡内容 |
| 性能 | 与关闭玻璃时比较，记录掉帧和资源开销 |

## 六、能否长期维护，主要取决于这些边界

### 1. 自定义部分集中管理，不要到处散改

我建议把新增的品牌、主题、动画和组件集中到独立目录，原页面只保留少量接入点：

```text

├─ 品牌配置与资源
├─ 颜色、圆角、间距、动画参数
├─ 玻璃底栏和通用组件
└─ 与原有任务操作连接的适配层

Mindwtr 原有实现
├─ 任务数据与业务逻辑
├─ 持久化与同步
└─ 其他跨平台能力
```

**不要全仓库搜索替换 `Mindwtr → Todo Moe`。** 应用显示名需要改，原作者声明、内部包名、数据字段、协议标识不一定该改。

品牌审查应覆盖应用名、图标、启动画面、包名、URI scheme、更新来源，以及涉及第三方服务的回调配置。不要默认上游的服务身份和你的新包名可以直接共用。

模块化能减少合并冲突，但不能保证以后永远没有冲突。

### 2. 日用版和开发版，不仅要分包名，还要分测试数据

这是很重要的一条：

> **不同包名只能隔离各自的本地应用空间；如果两个版本连着同一个同步目录，仍然会操作同一份云端待办。**

所以开发版默认使用独立测试数据、独立同步目录。真实任务迁入之前，先验证导出、导入、离线修改、同步和恢复流程。

Mindwtr 的 WebDAV 同步也不是“任何能存文件的 WebDAV 都行”：项目明确要求强 ETag 和条件写入等能力，应通过它的兼容性检查。citeturn446572view0

### 3. 固定签名密钥和版本策略，从第一版就确定

Android 覆盖升级涉及签名兼容性；对自行管理签名的发行方式，丢失签名密钥会直接影响后续更新能力。citeturn810937view3

因此我建议：

**正式版固定包名、固定发行密钥；开发版另用自己的身份。密钥加密备份，不放 Git，不写进 Issue，也不贴进 Codex 对话。**

同时，自己的 `versionCode` 要持续递增，不直接跟着上游版本号随意变化。Android 会用它防止安装更低版本。citeturn393760view0

应用“关于”页可以这样展示：

```text
Todo Moe 0.1.0
基于 Mindwtr：<上游版本>
上游提交：<SHA>
本应用提交：<SHA>
```

还有一点：**回退代码不等于回退数据库。** 出问题时不能默认旧 APK 一装就恢复，所以正式更新前的备份和迁移测试比“一键回滚”按钮更重要。

### 4. 保留许可和代码来源，不把整个项目改成 MIT

Mindwtr 当前声明的是 **AGPL-3.0-only**。SukiSU 的底栏入口文件虽然标注了 Apache 2.0 示例来源，但辅助代码和依赖仍需逐项核对。citeturn597486view0turn390565view4

我的建议是继续按上游许可维护派生项目，在发布时保留对应源码、构建说明和必要声明，并记录：

```text

对应哪个提交
复制或改编了哪些文件
保留什么许可证
你修改了什么
```

**改名字、换 Logo、让 Codex 重写一部分，不会自动消除原代码的许可要求。**

### 5. 自动化自身也需要验收

这里有两个很容易被 Codex 写漏的坑。

GitHub 对 `GITHUB_TOKEN` 触发后续工作流有限制；当前文档说明，机器人创建或更新某些 PR 时，CI 可能进入等待批准状态。不能只看到“PR 已创建”，就认定后续测试一定跑了。应明确设计工作流调用链并实际验证。citeturn390565view2

另外，公开仓库长期没有活动时，定时工作流可能被禁用；GitHub 文档给出的阈值是 **60 天**。所以必须保留一个手动触发入口，不把定时检查当作永远不会停的服务。citeturn142026view3

## 七、交给 Codex，我建议按这四步推进

**不要第一句话就让它“把整个 App 改漂亮”。** 先把可维护性和玻璃实现路线确定下来。

| 阶段 | Codex 要交付什么 | 你主要验收什么 |
|---|---|---|
| **① 建立基线** | 原版可复现构建；Todo Moe 独立身份；开发版；固定构建命令 | 能安装、能连续覆盖升级、数据不丢 |
| **② 玻璃验证** | 从你用成功的底栏版本开始，做 RN + 原生玻璃小样 | 真正动态模糊、手势正常、不卡 |
| **③ 日常体验** | 简化导航、文件夹清单、主题、完成动画、快速添加 | 每天用起来是否顺手 |
| **④ 更新闭环** | 上游同步 PR、检查、签名发布、手机更新配置 | 一次成功更新和一次冲突失败都能正确处理 |

每阶段保留可运行的提交，不做一次性大重构。尤其不要把“升级 Expo/RN”“换导航”“加玻璃”“改任务逻辑”全塞进同一个 PR。

Codex 的项目约束适合写进 `AGENTS.md`；官方文档明确说明它会读取这些项目指令。保留上游已有指导，再加入你的边界，而不是覆盖掉。citeturn390565view1

还有一个更正：**我上一条提到的 `bun mobile:android:dev`，在这次读到的根目录脚本中没有看到，不能作为现成命令直接照抄。** 让 Codex以实际 `package.json` 和工作流为准，补齐并验证自己的开发版命令。citeturn597486view1

**我的最终建议就是：选 `Todo Moe`，直接 Fork；先建立可升级的独立测试版，再把你已经喜欢的 SukiSU 底栏接通。视觉上做“玻璃操作层、清晰任务层”，维护上做“自动处理重复工作，异常才交给 Codex”。**
