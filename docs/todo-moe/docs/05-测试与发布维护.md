## 3. 性能验收方法

每次性能对照前确定设备、清单规模与预算，记录为该轮验收输入。最初聊天没有测量数据；后来取得的vc3限定lab近似指标见[玻璃记录](../GLASS.md)，不能外推到其他设备、完整场景、内存或功耗。

| 对照 | 记录内容 | 判定 |
|---|---|---|
| 玻璃关闭 / 柔和 / 液态 | 相同设备、列表、滚动路径、帧时间/掉帧、CPU、内存 | 按事先记录预算比较；不能凭录屏观感宣称无开销 |
| 简洁 / 标准 / 活泼动画 | 连续完成、快速添加、滑动阈值和列表收起 | 操作不排队、反馈准确、资源不持续累积 |
| 冷启动/热启动/切回前台 | 耗时、资源恢复与残留层 | 与基线比较，记录复现条件 |
| 小清单 / 大清单 | 数量、长文本、分组层次 | 大数据下仍可记录和完成，必要时降级效果 |
| 连续使用 | 崩溃、任务异常、同步失败、异常耗电观察 | 覆盖不足明确保留未验证；主观体感与测量值分开 |

门槛尚未确定时，版本状态写“待定义验收预算”，不能先把未知结果标绿。

## 4. 自动化设计

相关源码和工作流已推送，PR与远端CI已经运行，e6对应CI APK也已成功核验。本次5a36c0b1的自有check job已成功，Dev APK仍in_progress；Native Platform CI与Dependency Audit已成功，普通CI仍in_progress。精确job和同树合并源码见[验证记录](../VALIDATION.md)，不能把check通过等同APK完成。

2026-09-11T18:54:49.881Z实际discover读取稳定tag v1.2.8，其SHA `9f94211faecc2d1463403b7458069391f5c9d99c`已在5a36c0b1祖先中，因此no-update，未创建上游更新分支、PR或Codex定时任务。见[发现记录](../UPSTREAM-VALIDATION-20260912.md)。下图是有新目标时的流程设计，不表示所有远端分支已演练；Git源码同步与用户暂不启用的任务数据同步是不同事项。

```text
每天检查上游稳定 Release（并保留手动入口）
  ↓ 有新版本且尚未记录
创建/更新同步分支（同一上游目标去重）
  ↓
尝试 merge
  ├─ 冲突 → 停止，记录文件和基线，形成问题报告/Issue
  └─ 成功 → 创建/更新 PR，对合并后的准确提交运行检查
              ├─ 失败 → 停止，附命令和日志
              └─ 通过 → 测试 APK + 验收记录
                           ↓ 对具体提交完成发布审核
                         正式签名 → Release → 手机更新验收
```

| 流程 | 输入与产物 | 保护与验收 |
|---|---|---|
| moe-sync-upstream | 上次记录、上游稳定 tag/SHA → 同步 PR、上游差异记录 | 已有 PR 时更新/去重，冲突不强制覆盖；使用 [同步记录模板](templates/上游同步记录模板.md) |
| moe-check | 确切候选 commit → 类型/测试/构建结果、测试 APK | 不只确认“PR 创建成功”；验证后续检查真的运行且对应最新提交 |
| moe-release-android | 已验收 commit、递增 versionCode、版本记录 → 签名 APK、校验、Release | 正式签名环境受控，发行材料和源码对应；代码变了需重新验收 |
| moe-publish-existing | 原signed运行ID、批准SHA与versionCode → 只读预览，审批后消费同一审查工件公开 | 已有fake-gh拒绝/恢复测试；不重签、不覆写同版本工件，真实GitHub公开仍未验，见[发布流程](../RELEASE-FLOW-20260912.md) |
| 手机更新 | 指定仓库 Release 与正确渠道 | 首版建议 Obtainium 提醒后安装，验证稳定/测试筛选 |
| 异常处理 | 冲突、失败、缺权限、计划任务停用 | 输出可操作报告，保留手动触发；不伪造成功或反复发布 |

数据库迁移、同步协议、完成/重复任务语义、Android 权限、签名与工作流权限变化采用显式审核。正式签名凭据不交给生成自动修复代码的运行环境。具体 GitHub Token 事件传播与 schedule 限制见 [技术核对](04-技术来源与待验证事项.md)，创建流程时再实测权限和触发链。

未来如果选用 Codex GitHub Action 或其他云端代理，需要单独配置当时可用的认证与预算；当前没有这项部署，也不把本机桌面登录态当成 CI 凭据。

## 5. 签名、版本号与发布内容

| 项目 | 规则 |
|---|---|
| versionName | 本项目自己的语义版本，与 Mindwtr 版本分别展示；每个补丁/预发布单独落档 |
| versionCode | 同一包名内持续递增，独立分配，不直接跟随上游版本或本地时钟临时猜值 |
| 签名 | 同一发行渠道固定密钥，记录证书指纹；密钥和口令不入文档 |
| Release | 标题、渠道、tag、完整 commit、变更/已知问题/支持设备、源码、APK、SHA-256 相互对应 |
| 产物 | 测试包明确 Dev/预发布标识；APK 文件名包含应用名、版本、渠道和构建编号，实际命名基线阶段固定 |

建议在最早一次发布之前分配唯一构建编号策略，尤其避免同时从本机和 CI 构建时产生重复 versionCode。预发布使用例如 v0.3.0-alpha.1、v0.3.0-rc.1；修复版使用 v0.3.1。它们均是规则示例，不是现存版本。

文件命名示例：TodoMoe-0.3.0-dev-buildNN.apk。buildNN 是占位，不可当可安装包链接。真实产物建立后记录文件大小、SHA-256、包名、versionName/versionCode 和签名指纹。

## 6. 升级、回退与恢复

| 故障 | 处理方案 | 验收边界 |
|---|---|---|
| 视觉/手势回归 | 先关闭玻璃或简化动画，必要时回退相关代码并发更高 versionCode 修复包 | UI 回退不得重置用户数据 |
| 构建/工作流回归 | 保留上次已验证产物和流水线记录，修复后重建 | 不把历史成功日志贴到新提交 |
| 数据迁移或同步问题 | 停止进一步真实数据写入，使用隔离副本复现并按恢复演练处理 | 不能承诺旧 APK 一装即可回滚数据库 |
| 签名/包名不匹配 | 检查渠道、包名与证书指纹，再决定修复路径 | 不用卸载重装掩盖无法覆盖升级，也不未经授权删除数据 |
| 发布到错误渠道/元数据错 | 记录受影响产物和范围，修正发行记录，验证客户端选择 | 保留故障记录，不覆盖成“从未发生” |

真实任务迁入前，完成当前使用范围内的导出、导入、离线与备份恢复测试。本轮local-only不要求启用同步后端；将来用户选择同步时，再独立验证后端、对端和冲突恢复。数据格式变化时应备份并验证恢复能力；备份文件存在本身不等于可以恢复。

## 7. 每次版本开发怎样落文档

1. 开始工作前，从 [版本模板](templates/版本记录模板.md) 建立该具体版本文件，填写目标、范围、上游基线和当前状态。
2. 开发时记录实际修改、关键决策、偏离原计划的原因及对应代码位置；关键阶段保留可运行提交。
3. 构建时填写准确命令、环境、提交、构建编号、包信息和日志；相同版本的重建产物不得混用记录。
4. 验收后填写每个用例的实际结果、证据、缺陷和未验证事项；静态/构建/实机分开。
5. 交付时更新该版本文档、版本索引、开发台账与 CHANGELOG；通过的项才可标完成，缺陷修复形成下一份版本记录。

下一步：按[收尾记录](../FOLLOWUP-20260912.md)完成目录选择器受控切屏复测，并逐项补齐当前使用范围的设备矩阵；新候选另行记录，不预报尚未构建的APK结果。
